# Архитектура Backend Сервиса

данный гайд описывает желаемую архитектуру в общем виде. Отхождения от него возможны но требуют объяснения.

Примечание. Upsert — создание записи при отсутствии соответствующего id или обновление если такой есть 

## Общее

Приложение делится на 3 слоя:
- интерфейса сервера (API)
- корневой логики (domain)
- сохранения данных (repository)

## Интерфейсный слой

отвечает:
- получение информации от пользователя
- валидации полученной информации
- составления запроса к сервису
- получение ответа от сервиса
- отправка ответа сервиса пользователю
Состоит из handler, которые отвечают за взаимодействие с одним из сервисов приложения. В handler должен содержатся только один сервис, в одном методе должно быть не более одного вызова метода сервиса. Handler может содержать несколько методов относящихся к одному сервису.
При необходимости хранит DTO, Requers и Resonce модели. Маппинг из доменной модели в интерфейсную происходит в хендлере и является ответственностью интерфейсного слоя.
Логирование необходимо для входных данных пользователя, команд для сервиса, ответов сервиса.

## корневой слой

состоит из нескольких частей:
- сущностей (entity)
- сервисов (service)
- объектов значений (value Object)
логирование на данном слое запрещено. Так как он строго детерминирован при наличии данных.

Сущность (синоним Агрегата DDD) ответственна за основную бизнесс логику. Представляет из себя границу транзакции. Вызов метода сущности всегда оставляет её в валидном состоянии (иначе выбрасывается исключение). Сохранение сущности происходит целиком (upsert всех её полей).
Сущность не обращается к другим частям программы. Все необходимые данные должны быть в её состоянии, либо передаваться в качестве аргумента её метода. В идеальном случае Сущность не имеет импортов других компонентов (исключением могут быть типы id других сущностей пример: user.userId).
При создании сущности ID передаётся сверху (ответственным за организацию id является сервис с репозиторием)

Сервис отвечает за получение сущностей из хранилища. Вызов соответствующих методов сущностей. Сохранение обновлённого состояния сущностей. Сервис никогда напрямую не изменяет состояние сущности, только путём публичного интерфейса.
Сервис Может содержать несколько Сущностей, но не может вызывать другие сервисы. Главной задачей сервиса является оркестрация сущностей.
Сервис может вызывать несколько репозиториев в одном методе, но в таком случае все взаимодействия с репозиториями обязаны проходить в одной транзакции.

## Слой Данных

состоит из репозиториев. каждый репозиторий должен минимально реализовывать:
- save(Entiry) → entityId, error (upsert всего состояния сущности)
- take(entityId) → Entity, error (создание сущности на основе сохранённых данных)
логирование данных о состоянии поступаемых и возвращаемых сущностей.
